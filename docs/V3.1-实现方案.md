> 目标：把「手机遥控单任务」升级成「掌上多任务中控台 + 全生命周期可视化 + 桌面会话审批也能管 + 手机直传文件」。

## 0. 现状基线（已实测，不是猜的）

| 项 | 实况 |
| --- | --- |
| 服务端 | `bridge/server.js`（约 700 行，node 原生 http + 手写 WS + TCP 8787 审批口），常驻后台 job |
| 任务执行 | `spawn('dsh --profile headless --json "<prompt>"')`，一个进程一个任务，`current` 单槽 |
| 审批来源 | 只有 headless 进程被我们注入的插件（`dsh-approval-bridge`）能拦到 → 转发 TCP 8787 → 手机 |
| 桌面端审批 | 走 DSH 桌面进程内的 waterfall，我们**看不到也管不了**（手机收不到，也无法代批） |
| 会话 | `--session-id` 只能续**已存在**的会话；新任务必须省略，`sessionId` 从事件流里取 |

**实测事件契约**（`dsh --profile headless --json`，逐行 JSON）：

| type | 载荷 | 用途 |
| --- | --- | --- |
| `session` | `{sessionId:"session-<uuid>", cwd}` | **新任务的 sessionId 来源** |
| `status` | `{phase:"turn_start"\|"step_start"\|..., turn, step}` | 状态机心跳 |
| `thinking` | `{text}` | 轨迹（思考） |
| `tool_call` | `{callId, tool, input:{...}}` | 轨迹（调用） |
| `tool_result` | `{callId, status:"completed"\|..., result}` | 轨迹（结果） |
| `text` | `{text}` | 流式正文 |
| `final` | `{text}` | **成功终态** |
| `error` | `{message}` | **失败终态** |

已实测：续会话 `--session-id session-08ee8f56-...` 成功，`status.turn` 从 1 递增到 2（说明上下文真的接上了）。

## 一、全生命周期轨迹与状态（服务端 + 前端）

### 1.1 服务端：事件归一化
新增 `normalizeEvent(raw, task)`，把 dsh 的 8 种事件压成 3 类下发：

```jsonc
// 1) 轨迹（前端直接渲染，不再自己猜字段）
{"type":"trace","data":{"taskId":"t1","kind":"thinking","brief":"思考：The user asks to run echo hi…","detail":"全文","at":1699...}}
{"type":"trace","data":{"taskId":"t1","kind":"tool_call","brief":"pwsh: echo hi","detail":"{\"description\":\"...\",\"command\":\"echo hi\"}"}}
{"type":"trace","data":{"taskId":"t1","kind":"tool_result","brief":"已完成 · hi","detail":"hi\r\n"}}
{"type":"trace","data":{"taskId":"t1","kind":"final","brief":"任务完成","detail":"完整回复"}}

// 2) 任务状态机（状态栏用）
{"type":"task-state","data":{"taskId":"t1","state":"running","phase":"step_start","turn":1,"step":2}}
{"type":"task-state","data":{"taskId":"t1","state":"success","taskId":"t1","durationMs":8421}}
{"type":"task-state","data":{"taskId":"t1","state":"failed","reason":"unknown option '-n'"}}
{"type":"task-state","data":{"taskId":"t1","state":"stopped"}}
```

状态判定规则（写死，避免歧义）：
- 收到 `final` → `success`
- 收到 `error` → `failed`（带 `message`）
- 进程退出码 ≠ 0 且未收到 `final` → `failed`（带尾部 stderr 200 字）
- 用户点停止 → `stopped`
- 进程存活但 10 分钟无任何事件 → `failed`（reason=`任务无响应超时`）

### 1.2 前端渲染
- 轨迹面板条目：`▶/▼ [图标] brief` → 展开显示 `detail`（等宽字体、可滚动、超 4000 字截断 + 「…」）。
- 四类都渲染：思考（灰蓝）、工具调用（蓝）、工具结果（绿/红）、最终输出（白，面板底部固定块）。
- 状态栏：`执行中…`（呼吸蓝）/ `任务成功`（绿）/ `任务失败`（红 + 原因一行）/ `已停止`（灰）。
- 轨迹随任务切换：每个任务独立存 `List<TraceEntry>`（客户端内存 + 服务端回放接口，见 3.4）。

## 二、电脑端审批也要推手机（重点、有代价）

### 2.1 为什么会漏
电脑端弹窗是 **DSH 桌面进程内**的 `approval/request` waterfall，跟我们的 headless 子进程是两套进程。手机要「看见并且能批」，就必须在那个进程里放一个 answerer。

### 2.2 三条路径对比

| 方案 | 能看见 | 能代批 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| **B1 插件注入 web profile（推荐）** | ✅ | ✅ | 需要改 `profiles\web\package.json` + 建 junction + **重启 DSH 桌面**（当前会话 UI 会断） | 唯一能真正闭环 |
| B2 轮询 session 日志旁路 | ⚠️只能看到「有审批在等」，拿不到可用的审批 id | ❌ 批不了 | 只读，无风险 | 作降级方案 |
| B3 代理 dsh web HTTP API | ❌ 没有公开审批端点，要偷 token | ❌ | 脆、易碎 | 不采用 |

### 2.3 B1 具体做法
1. `D:\DeepSeekHarness\dsh_data\profiles\web\package.json` 加：
   ```json
   "dependencies": { "dsh-approval-bridge": "link:D:/DeepSeekHarness/project3-DaiDaiFish-DSH-Bridge/DaiDaiFish-DSH-Bridge/dsh-approval-bridge" },
   "dsh": { "profile": { "bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app", "dsh-approval-bridge"] } }
   ```
   （该 profile 目前**没有** `node_modules` 目录，需新建 junction）
2. 插件升级为「带来源与降级」：
   - 转发时带 `origin:"desktop"`、`workspace`（取 `req.agent` 的 cwd/工作区，取不到则 `process.cwd()`）、`sessionBrief`（取不到则 `-`）、`reason`。
   - **fail-open**：桥回 `{outcome:'unavailable'}`（手机不在线/超时）→ 插件 `return undefined`，让 DSH 桌面自己的弹窗照常出现，行为**完全不变**。
   - 手机真答了 → 返回 `allowed-once`/`rejected`，桌面那边同一请求被抢先应答（弹窗自动消失，合理）。
3. 手机端待审批列表显示格式：`[工作区名] - [会话简述] - [审批内容]`，例：
   `[project2-逆向] - 删除临时文件 - pwsh: 需要在工作区外删除 xxx.txt`。
4. 验收：桌面上让 DSH 执行一个越权删除 → 手机收到 → 手机点「允许一次」→ 桌面命令成功执行，且桌面弹窗没卡住。

> ⚠️ 这一条**必须重启桌面 App**才生效。重启会中断老大当前正在用的这个会话窗口（历史不丢，UI 重开）。所以我把 B1 排到最后一批，等你点头 + 挑时间。

## 三、多会话与多任务隔离

### 3.1 任务模型（服务端）
```js
tasks = Map<taskId, {
  taskId, proc, pid, sessionId,   // sessionId 来自 session 事件
  workspace, prompt, startedAt,
  state: 'running'|'success'|'failed'|'stopped',
  trace: [],                      // 最近 200 条，供切换回放
  stderrTail: ''
}>
```
- 新任务：**省略** `--session-id` → 从 `session` 事件抓 `sessionId` → 绑定。
- 续会话：`{action:"run", prompt, sessionId:"session-xxxx"}` → 传 `--session-id`。
- 并发上限 `MAX_TASKS = 2`（可配）。第 3 个直接回：
  `{"type":"error","code":"BUSY","message":"已有 2 个任务在跑，先停一个"}`（不做排队，避免"点了没反应"的体感）。
- 停止：`{action:"stop", taskId}` → `taskkill /pid <pid> /T /F`（沿用已验证方案）。

### 3.2 协议扩展（手机 → 服务端）
| action | 参数 | 说明 |
| --- | --- | --- |
| `run` | `prompt, workspace?, sessionId?, newTask?` | `newTask:true` 强制新开会话 |
| `stop` | `taskId` | 停指定任务 |
| `tasks` | - | 拉任务列表 |
| `switch-task` | `taskId` | 切换当前查看（触发 trace 回放） |
| `workspaces` / `create-workspace` | 同现有 | 不变 |

### 3.3 服务端 → 手机
- 所有 `trace`/`task-state`/`stdout`/`stderr` 都带 `taskId`。
- 新增 `{"type":"tasks","data":[{taskId,sessionId,workspace,prompt,state,turn,startedAt}]}`。
- 新增 `{"type":"task-trace","data":{"taskId":"t1","entries":[...]}}`（切任务时回放）。
- `approval-request` 增加 `taskId`、`origin`、`workspace`、`sessionBrief` 字段。

### 3.4 前端
- 顶部加【+ 新建任务】→ 清空当前视图、开新任务、`newTask:true`。
- 加任务切换条（横向标签：`pwsh·执行中` / `#2·成功`），点击切任务、回放轨迹。
- 停止按钮作用于「当前选中任务」。

> 说明：会话历史仍由 DSH 自己存盘（`dsh_data\sessions\...`），我们只做**进程生命周期 + 会话 id 绑定**，不复制、不改写它的存储。

## 四、手机端文件/图片上传（分片）

### 4.1 协议（文本分片，零改动 WS 解析层）
```jsonc
手机 → {"action":"upload-begin","uploadId":"u1","name":"bg.jpg","size":308906,"workspace":"D:\\...","taskId":"t1"}
服务 → {"type":"upload-accept","uploadId":"u1","maxChunk":65536}
手机 → {"action":"upload-chunk","uploadId":"u1","seq":0,"dataB64":"...."}   // 原始 64KB/片
服务 → {"type":"upload-progress","uploadId":"u1","received":131072}
手机 → {"action":"upload-end","uploadId":"u1"}          // 可带 sha256 校验
服务 → {"type":"upload-done","uploadId":"u1","path":"<workspace>\\uploads\\bg_1699.jpg","size":308906}
```
- 落盘：`<任务 cwd>/uploads/<原名>_<时间戳>.<ext>`，**只取 basename**（防 `../` 穿越），同名自动加时间戳。
- 限额：单文件 ≤ 50MB、单任务累计 ≤ 200MB；超限回 `{"type":"error","code":"TOO_LARGE"}`。
- 为什么用 base64 而不是二进制帧：现有手写 WS 服务端只解析文本帧，改二进制要动帧解析层（风险高）。base64 体积 +33% 但零风险，先用它。

### 4.2 prompt 自动带路径
手机发 `run` 时带上 `attachments:[uploadId...]`，服务端在 prompt 末尾追加：
```
附件（请用工具读取）：
- D:\...\uploads\bg_1699.jpg
```

### 4.3 前端
- 控制台加【📎 上传文件】→ `Intent.ACTION_GET_CONTENT`（`image/*` + `*/*`）→ 读流分片 → 进度条 + 取消。
- 上传完成把路径塞进输入框上方的「待发送附件」小标签（可删）。

## 七、风险与回滚
| 风险 | 处置 |
| --- | --- |
| P4 重启桌面中断当前会话 | 放最后一批，你挑时间；不点也行，B2 降级只做通知 |
| 多任务并发打爆 API 配额/内存 | 上限 2，`MAX_TASKS` 可配；超了明确报 BUSY |
| 上传大文件撑爆 WS 背压 | 64KB 分片 + 50MB 上限 + 进度回执 |
| 新 APK 装不上/签名异常 | 沿用已修好的签名校验绕过 + debug 签名；旧 APK 全部保留 |
| 改动过大出回归 | 每批先跑探针再打包；`git` 分批 commit，随时 `git revert` |
